# 外部库 API 调用与返回值处理规范

> 状态：已对齐  ｜ 适用范围：`src/`、`examples/`、`bsp/` 中调用第三方库、Arduino 框架 API 或硬件驱动 API 的代码
> 最后对齐：2026-09-18 ｜ 上游：ARC-01、SPEC-T ｜ 文档编号：DD-04

## 1. 目的

本规范用于解决分层开发中最容易被忽略的一类问题：外部 API 的返回值语义、对象状态和调用副作用可能与项目代码的直觉假设不同。

项目代码不得仅凭函数名、返回类型或常见编程习惯推断“成功”含义。调用外部 API 时，必须先确认其契约，再将外部语义转换为项目内部统一语义。

本规范尤其适用于：

- 电机驱动、传感器、功率、电源和通信初始化；
- 校准、参数保存、参数读取和硬件配置；
- 控制环、状态机和周期任务依赖的外部库调用；
- Arduino、ESP32、SimpleFOC 及其他第三方库接口。

## 2. 核心原则

### 2.1 先确认契约，再编写判断

调用前至少确认以下信息：

| 项目 | 必须确认的内容 |
| --- | --- |
| 返回值语义 | 哪个值表示成功、失败、未完成或部分成功 |
| 返回值类型 | `bool`、整数错误码、枚举、状态码、长度或句柄 |
| 对象状态 | 调用后哪些字段会被更新，哪些字段才是最终状态依据 |
| 副作用 | 是否会启动硬件、阻塞等待、改变模式、写入 NVS 或消耗资源 |
| 版本差异 | 当前安装版本与参考文档、示例、源码是否一致 |
| 失败条件 | 失败时是否需要释放资源、重试、复位或进入安全状态 |

证据优先级为：当前实际依赖版本源码和头文件、当前版本官方文档、官方例程、项目既有实测记录、个人经验推断。若证据不足，必须标记为“待验证”，不能把推测当作契约。

### 2.2 保存原始返回值，再执行判断

关键外部调用禁止直接嵌入 `if`、`while`、三元表达式或复合布尔表达式。推荐使用以下顺序：

```cpp
auto rawResult = externalApi();
logExternalResult("externalApi", rawResult);

bool ok = convertToProjectSuccess(rawResult);
if (!ok) {
    handleFailure();
}
```

原因是：

- 原始返回值可以直接证明外部库实际返回了什么；
- 调试日志不会被 `!`、隐式转换或短路求值掩盖；
- 项目内部判断与外部库语义可以分开验证；
- 以后更换库版本时，能快速发现契约变化。

以下写法只允许用于已经被项目适配层统一成明确 `bool` 语义的函数：

```cpp
if (!motorAdapter.init()) {
    enterSafeState();
}
```

此处的 `motorAdapter.init()` 必须是项目自己的适配函数，不能直接等同于第三方库的原始接口。

### 2.3 外部语义必须转换成项目语义

外部库的原始返回值不应在业务代码中到处解释。适配层负责完成以下工作：

1. 调用外部 API；
2. 保存并记录原始返回值；
3. 检查必要的对象状态字段；
4. 将外部语义转换成项目统一的 `true = 成功`、`false = 失败`；
5. 按项目状态机处理失败、重试和安全退出；
6. 在注释中写明特殊返回约定和证据来源。

推荐形式：

```cpp
bool initDriver() {
    int raw = driver_.init();
    bool initialized = driver_.initialized;

    Serial.printf(
        "[ADAPTER] driver.init raw=%d initialized=%d\\n",
        raw,
        initialized ? 1 : 0
    );

    // 当前依赖版本约定：raw == 0 表示成功。
    return raw == 0 && initialized;
}
```

适配层的返回值必须在函数命名、注释和日志中保持一致。若外部 API 返回的是长度、状态枚举或句柄，不得直接把“非零”作为通用成功判断，必须根据该 API 的具体契约转换。

## 3. 返回值语义检查清单

在使用新的外部 API 或升级依赖版本时，逐项完成以下检查：

- [ ] 阅读当前依赖版本的声明、实现或官方文档；
- [ ] 明确成功值、失败值、未完成值和部分成功值；
- [ ] 明确返回值是否可能为负数、零、正数或位掩码；
- [ ] 确认返回值是否只是“调用已接受”，而非“动作已完成”；
- [ ] 确认最终结果是否还需要检查对象状态字段；
- [ ] 确认调用是否修改模式、硬件输出、参数存储或通信状态；
- [ ] 用日志记录一次真实调用的原始返回值；
- [ ] 为项目内部判断写一个清晰的转换函数；
- [ ] 对失败路径进行一次可重复的实验验证；
- [ ] 将证据、版本号和结论写入对应文档或调试日志。

## 4. 关键路径日志规范

### 4.1 必须记录的阶段

以下阶段必须至少记录“进入、原始返回值、转换后的判断、退出状态”：

- 电源和驱动初始化；
- 电机、传感器和编码器初始化；
- FOC 对齐与校准；
- 参数加载与保存；
- 串口、总线和上位机协议握手；
- 控制模式切换；
- 进入安全状态、重试或永久停机。

推荐日志字段：

```text
[模块] 阶段 action=... raw=... status=... ok=... reason=...
```

示例：

```text
[MOTOR] driver.init raw=0 initialized=1 ok=1
[MOTOR] motor.initFOC raw=1 status=4 ok=1
```

### 4.2 日志必须能够区分四种值

不要只打印“成功/失败”。日志应尽可能同时保留：

1. 外部 API 原始返回值；
2. 外部对象状态字段；
3. 项目转换后的布尔或枚举状态；
4. 失败时的原因、阶段和后续动作。

这样可以区分“外部调用失败”“外部调用成功但对象未就绪”“项目转换错误”和“后续状态机错误”。

### 4.3 日志不可改变关键时序

调试打印应使用已有串口或日志设施，避免在实时控制拍中加入无界阻塞。初始化和实验阶段可以提高日志详细度；进入稳定控制阶段后，应采用节流、级别开关或一次性打印。

日志内容不得替代正确的状态判断。打印返回值后，仍必须执行经过确认的项目逻辑。

## 5. 初始化与失败处理

关键初始化流程采用“阶段化”结构：

```text
进入阶段
  ↓
调用外部 API
  ↓
记录原始返回值和对象状态
  ↓
转换为项目状态
  ↓
成功：进入下一阶段
失败：记录原因并进入明确的安全路径
```

失败路径必须明确属于以下之一：

- 可重试：记录次数和间隔；
- 可降级：记录降级能力和限制；
- 必须停机：关闭输出并保持安全状态；
- 等待外部条件：说明等待条件和超时策略。

禁止使用无限等待掩盖未解释的失败。若确实需要保持安全停机，必须在循环前打印阶段、原始返回值、对象状态和停机原因。

## 6. 版本和证据管理

外部 API 的语义与版本相关时，文档和日志至少记录：

- 库名称和版本；
- 芯片、板卡和编译环境；
- API 函数名或类方法名；
- 参考源码、头文件、官方文档或例程位置；
- 实测原始日志；
- 项目适配函数和关联代码提交。

证据按项目调试日志约定分级：

- **A**：实测且原始数据已落盘；
- **B**：实测但原始数据未落盘；
- **C**：基于代码、原理或文档的推理；
- **D**：待验证推测。

当源码证据与个人直觉冲突时，以当前依赖版本的源码和可重复实测为准，并把被证伪的判断保留在对应经验日志的“假设坟场”中。

## 7. 禁止模式与推荐模式

### 7.1 禁止模式

```cpp
if (!driver_.init()) {
    return false;
}
```

当 `driver_.init()` 的契约是 `0 = 成功` 时，上述写法会把成功误判为失败，而且日志中没有留下原始证据。

### 7.2 推荐模式

```cpp
int driverRet = driver_.init();
bool initialized = driver_.initialized;

Serial.printf(
    "[MOTOR] driver.init raw=%d initialized=%d\\n",
    driverRet,
    initialized ? 1 : 0
);

if (driverRet != 0 || !initialized) {
    return false;
}
```

更推荐把这段逻辑封装在适配层中，让上层只依赖项目自己的明确接口：

```cpp
if (!motorAdapter.initDriver()) {
    return false;
}
```

## 8. 评审与验收要求

涉及外部 API 的代码提交，在评审时至少回答：

1. 这个返回值的成功语义由什么证据确认？
2. 原始返回值在哪里保存和记录？
3. 是否还需要检查对象状态字段？
4. 外部语义在哪里转换成项目语义？
5. 失败后的重试、降级或安全停机路径是什么？
6. 是否有实测日志或可复现验证？
7. 依赖升级后，哪些契约需要重新确认？

未能回答上述问题时，代码应保持为待验证状态，不得将其作为已闭环的初始化或验收依据。

## 9. 与项目文档的追溯关系

本规范属于 L5 详细设计层，负责规定外部 API 在代码中的落地方式。具体问题的排查证据和经验复盘放在 L6 调试日志，不在本文件中展开为流水账。

推荐追溯链：

```text
规格条款 / 测试门禁
    ↕
本规范与具体适配层设计
    ↕
代码中的适配函数和外部 API 调用
    ↕
原始串口日志、实验记录和经验帖
```

本规范的具体经验示例见后续 L6 经验日志；当前 SimpleFOC 驱动初始化返回值语义问题应作为独立经验帖记录，不在本规范中替代实验记录。

## 10. 完成定义

一处外部 API 调用满足以下条件，才可标记为已完成：

- 返回值契约已确认并记录来源；
- 原始返回值已保存并可在调试日志中看到；
- 必要的对象状态已检查；
- 外部语义已转换为项目内部语义；
- 失败路径和安全行为已明确；
- 至少完成一次可重复验证；
- 关联代码、文档和实验记录能够相互追溯。
