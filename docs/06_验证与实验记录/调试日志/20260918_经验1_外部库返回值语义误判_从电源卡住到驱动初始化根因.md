## 0. 本篇只讲三条

1. 外部库的返回值语义不能凭函数名、返回类型或“非零表示成功”的习惯判断，必须核对当前依赖版本的源码、头文件或官方文档。[B-代码事实]
2. 关键外部调用必须先保存并打印原始返回值，再转换为项目内部的成功/失败语义；把调用直接嵌进 `if` 会把最有价值的诊断证据丢掉。[B-代码事实 + C-推断]
3. 本次程序表面上像是卡在电源检测，实际是 `driver.init()` 成功返回 `0` 后被 `!` 误判为失败，`motor.init()` 因此向上层返回失败并进入停机循环。[B-代码事实 + 转引实测]

## 1. 病情陈述

固件启动时能够完成 `power.waitReady()`，串口打印电源已就绪；随后进入 `motor.init()`，上位机看不到正常的参数和协议响应，现场感觉像“电源检测通过后卡住”。真正的问题发生在更深一层：SimpleFOC 的 `BLDCDriver3PWM::init()` 在当前版本中以 `0` 表示成功，而项目旧代码使用 `if (!driver_.init()) return false;`，把成功值转换成了失败条件。[B-代码事实]

这个现象容易误导排查，因为最后一条正常的上层日志是电源阶段，而错误判断发生在电机适配层内部，没有留下原始返回值。

## 2. 事实链

### 2.1 现场启动顺序

启动日志的关键顺序如下。完整材料来自 2026-09-18 会话粘贴件，当前按“转引实测”使用：

```text
[FW BOOT] Serial.begin done
[FW BOOT] earlyInit done
[FW BOOT] power.begin done
电源就绪 11.93V
[FW BOOT] power.waitReady returned
[FW BOOT] motor.init enter
[FW BOOT] motor.init failed; halted
```

这段日志能证明：

- 串口启动完成；
- `earlyInit()` 完成；
- `power.begin()` 完成；
- 电源等待函数返回；
- 上层 `motor.init()` 最终返回失败并进入 `while (true) delay(1000)` 停机路径。[转引实测 + B-代码事实]

它不能单独证明“电源模块有故障”，因为“电源日志是最后出现的日志”不等于“故障发生在电源模块”。

### 2.2 旧代码的判断点

在调试插桩之前，`SimpleFocMotor::init()` 使用了以下关键路径：

```cpp
driver_.voltage_power_supply = vin;
if (!driver_.init()) return false;
motor_.linkDriver(&driver_);
```

这段代码把第三方库调用直接放进了条件表达式：没有保存原始返回值，也没有记录 `driver_.initialized` 等对象状态。[B-代码事实，提交 `964d830` 的父版本]

### 2.3 插桩后的证据

为区分“电源等待失败”“驱动初始化失败”和“适配层判断错误”，提交 `964d830` 在调用前后增加了阶段日志和原始返回值记录：

```cpp
Serial.println(F("[EXP MOTOR] driver.init enter"));
int driverRet = driver_.init();
Serial.printf("[EXP MOTOR] driver.init ret=%d initialized=%d voltage_limit=%.4f\\n",
              driverRet,
              driver_.initialized ? 1 : 0,
              (double)driver_.voltage_limit);
```

运行日志随后确认：

```text
[EXP MOTOR] driver.init ret=0 initialized=1
MOT: Align sensor.
MOT: Align current sense.
MOT: Ready.
[EXP MOTOR] motor.initFOC ret=1 status=4
[FW BOOT] setup complete
```

这些日志说明驱动初始化确实完成，后续 FOC 对齐、当前采样对齐和启动流程也继续执行。[转引实测]

## 3. 初始假设与误判

### 3.1 初始假设：问题卡在电源

这个假设的依据是：

- 最后一次稳定出现的上层日志是 `power.waitReady returned`；
- 程序没有进入上位机可交互状态；
- 外部表现像是“上电后不再继续”。

但这个假设把“最后一个可见日志点”误当成了“故障发生点”。日志只能说明电源阶段已经返回，不能说明下一阶段的内部调用结果。

### 3.2 隐含假设：非零表示成功

代码中的 `!driver_.init()` 暗含了一个没有写出来的契约：假定 `driver_.init()` 返回非零表示成功、返回零表示失败。这是许多 `bool` 风格 API 的常见习惯，但它不适用于当前 SimpleFOC 版本。[C-推断，基于旧代码表达式]

真正的契约必须从当前库源码确认，而不是从 `!` 的写法反推。

### 3.3 为什么错误没有立刻暴露

旧代码同时存在三个可见性缺口：

1. 原始返回值没有保存；
2. 第三方对象的 `initialized` 状态没有打印；
3. 失败只在上层表现为一个笼统的 `motor.init failed`。

因此，`0` 既可能被解释成“调用失败”，也可能被解释成“库约定的成功码”；没有原始值和源码契约，就无法在日志层区分两者。

## 4. 排查过程与转折点

### 4.1 先把问题分层

排查没有继续围绕“电源是否正常”猜测，而是把启动链拆成阶段：

```text
Serial.begin
  → earlyInit
  → power.begin
  → power.waitReady
  → motor.init
      → wire.begin
      → sensor.init
      → driver.init
      → currentSense.init
      → motor.init
      → motor.initFOC
  → setup complete
```

每个外部调用增加进入、返回和状态日志，目标是找到第一个“阶段已进入但没有有效后置状态”的位置。[B-代码事实]

### 4.2 再保存原始返回值

插桩后，`driver.init()` 的真实返回值第一次出现在日志中：`ret=0`；同时对象状态为 `initialized=1`。这组值与“0 是失败”的直觉冲突，但与“库内部已完成初始化”一致。[转引实测]

### 4.3 最后回到依赖源码确认契约

核对 SimpleFOC 2.2.1 的驱动初始化实现后，确认其行为是：设置驱动初始化状态，然后返回 `0`。因此该接口的成功语义是：

```text
driver.init() 返回 0 = 成功
driver_.initialized == true = 对象已初始化
```

这一步把“日志看起来矛盾”转化成了明确的 API 契约问题。[B-代码事实]

### 4.4 因果还原

旧判断的实际求值过程是：

```text
driver_.init() → 0
!0            → true
return false  → SimpleFocMotor::init() 失败
motor.init()  → false
setup()       → while (true) 停机
```

因此，“卡在电源”只是观察位置；根因是适配层把外部库的成功值错误转换成了项目失败语义。[C-推断，已由日志和源码共同支持]

## 5. 根因、修复与验证

### 5.1 根因

根因不是电源电压异常，也不是上位机先发命令导致的协议问题，而是外部库返回值语义在适配层被误读：

```text
外部契约：0 = 成功
项目判断：!0 = true → 进入失败分支
```

这是一个典型的“跨库接口语义转换错误”。它发生在项目代码和第三方库之间，属于适配层问题。[B-代码事实 + C-推断]

### 5.2 修复与诊断方式

修复的关键不是简单换一个 `!`，而是先把原始返回值和对象状态显式保存：

```cpp
int driverRet = driver_.init();
bool initialized = driver_.initialized;

Serial.printf("[EXP MOTOR] driver.init ret=%d initialized=%d\\n",
              driverRet, initialized ? 1 : 0);

// 当前 SimpleFOC 2.2.1 约定：ret == 0 表示成功。
if (driverRet != 0 || !initialized) {
    return false;
}
```

更长期的做法是把这段解释封装在项目自己的适配函数中，让上层只依赖明确的 `true = 成功` 接口，详见 `DD-04`。

### 5.3 验证结果

插桩后的日志继续出现：

```text
MOT: Align sensor.
MOT: Align current sense.
MOT: Ready.
[EXP MOTOR] motor.initFOC ret=1 status=4
[FW BOOT] setup complete
```

这证明启动流程越过了原先的停机位置，且 FOC 初始化完成。[转引实测]

本篇仍保留一个证据限制：上述串口内容来自会话粘贴件，当前没有在项目 `docs/06_验证与实验记录/波形与数据/` 中找到逐字原始文件。因此本篇不把这些日志标为 A 级，也不把它作为独立的正式上板验收记录。

## 8. 方法论与迁移用法

### 8.1 外部 API 的四步接法

以后调用任何外部库，关键路径统一采用：

```text
确认契约
  → 保存原始返回值
  → 记录对象状态和副作用
  → 转换为项目内部语义
```

对应代码形态：

```cpp
auto rawResult = externalApi();
logExternalResult("externalApi", rawResult);
bool ok = convertToProjectSuccess(rawResult);
if (!ok) {
    handleFailure();
}
```

### 8.2 初始化卡住时的最短排查路径

1. 找到最后一条已确认返回的阶段日志；
2. 不把最后日志点直接当成根因，继续进入下一层；
3. 对每个外部调用打印进入、原始返回值和对象状态；
4. 核对当前依赖版本的实现，而不是只看函数名；
5. 将外部返回值转换成项目内部 `true = 成功` / `false = 失败`；
6. 验证失败路径是否真的对应硬件失败，而不是语义误判；
7. 将原始日志落盘，再更新经验帖和索引。

### 8.3 适配层的职责

适配层不只是“把库函数调用放进项目”。它还必须承担：

- 外部返回值语义翻译；
- 对象状态和调用副作用检查；
- 版本契约记录；
- 关键阶段诊断日志；
- 失败、重试和安全停机策略。

如果这些工作散落在上层业务代码中，下一次更换库版本或调用路径时，错误很容易重新出现。
