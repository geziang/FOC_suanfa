# 经验日志写作规范

> 用途：规定 `调试日志/` 中经验帖的写作方法、证据纪律和完成定义。
> 适用范围：本项目所有 `YYYYMMDD_经验N_标题.md` 文件。
> 与 `_说明.md` 的关系：`_说明.md` 说明目录定位和文档分工；本文件说明一篇经验帖应该怎样写。

## 1. 经验帖是什么

经验帖是一次故障、误判或验证转折的复盘文档。它要回答：

- 现象是什么，触发条件是什么；
- 当时有哪些假设，为什么其中一些看起来合理；
- 哪条证据改变了排查方向；
- 根因如何被证实或仍然为什么不能下结论；
- 修复或实验为什么有效；
- 下次遇到类似问题，应该先检查什么。

经验帖不是串口流水账、单次上电实验表、标定参数报告，也不是代码变更说明。原始串口、波形、CSV 和完整实验条件应放在 `../波形与数据/` 或上级实验记录中；经验帖引用这些材料，并解释它们如何改变判断。

## 2. 命名、编号与状态

### 2.1 文件命名

统一使用：

```text
YYYYMMDD_经验N_标题.md
```

其中 `N` 是本项目经验帖的独立序号，从经验 1 开始，不与其他项目的经验编号混用。标题应写出收获、转折或根因，例如：

```text
20260918_经验1_外部库返回值语义误判_从电源卡住到驱动初始化根因.md
```

避免使用只描述动作的标题，例如“增加打印”“修改初始化”。

### 2.2 文头必须包含

每篇经验帖开头至少写明：

```markdown
> 专题：……
> 状态：……
> 硬件 / 固件 / 依赖版本：……
> 一手数据：……
> 证据可用性声明：……
> 姊妹篇 / 关联规范：……
```

状态必须使用项目现行状态词。没有可追溯的实验记录时，不得写“上板验证通过”；问题没有闭环时，应保持挂账状态并列出待验证项。

## 3. 推荐章节结构

复杂度不足的主题可以合并章节，但不得省略证据、误判和当前状态。

```markdown
# 经验N · 标题

> 文头元数据

## 0. 本篇只讲几条
## 1. 病情陈述
## 2. 事实链
## 3. 初始假设与误判
## 4. 排查过程与转折点
## 5. 根因、修复与验证
## 6. 预测—实测回填
## 7. 假设坟场
## 8. 方法论与迁移用法
## 9. 当前状态与下一步
## 10. 一句话带走
```

### 3.1 本篇只讲几条

开头用两到四条写读者最应该带走的经验。这里只写已经有证据支持的结论；尚未判决的内容放到后文并标注证据等级。

### 3.2 病情陈述

用一句话描述异常和触发条件。应区分“什么时候发生”和“什么时候不发生”，例如“电机驱动初始化后停机，而电源等待阶段已正常返回”，不要只写“程序卡住”。

### 3.3 事实链

按日志、实验记录和源码事实还原问题。每个关键数值、状态和时间顺序都要能回到原始材料，不能依靠记忆补写现场。

### 3.4 初始假设与误判

记录当时为什么会相信某个解释，以及它依赖了什么隐含前提。错误假设不能删除；要说明后来哪条证据推翻了它。

### 3.5 排查过程与转折点

重点写“为什么做这个实验”和“结果如何改变下一步”，而不是罗列执行过的命令。转折点应指出具体日志、源码契约或对照实验。

### 3.6 根因、修复与验证

把根因、修复动作和验证结果分开写。修复有效不等于已经证明唯一根因；如果仍有竞争解释，应继续挂账。

## 4. 证据等级纪律

所有结论使用以下标签：

| 标签 | 含义 | 允许写法 |
| --- | --- | --- |
| `[A-实测]` | 串口原文、仪器读数或操作者直接观察，且原始材料已落盘 | 可作为实验事实和验收依据 |
| `[B-代码事实]` | 对当前项目源码、依赖源码、头文件或配置的核查结论 | 可作为实现事实，不替代硬件实测 |
| `[C-推断]` | 由 A/B 推导出的解释，尚未由判决实验直接确认 | 必须明确写“推断”或“候选” |
| `[D-存疑]` | 原始证据缺失、冲突或存在多个竞争解释 | 只能作为待验证假设 |

要求：

- `[C-推断]` 和 `[D-存疑]` 不得写成 TL;DR 中的肯定根因；
- 经验帖中的关键结论必须注明证据来源或章节；
- 实测但原始数据未落盘时，必须明确标为转引证据，不能伪装成 A 级；
- 当前库版本源码证据与直觉冲突时，以当前版本源码和可重复实测为准，并记录版本号。

## 5. 外部 API 和代码证据

涉及第三方库、框架或硬件驱动时，必须写清：

- 库名称、版本和平台；
- API 函数、类方法或稳定代码符号；
- 成功、失败、未完成和部分成功的返回值语义；
- 调用后的对象状态和副作用；
- 参考源码、头文件、官方文档或例程的位置；
- 项目适配层如何把外部语义转换成内部语义。

关键调用的排查日志应优先保留原始返回值，再写项目判断结果。例如：

```cpp
auto rawResult = externalApi();
logExternalResult("externalApi", rawResult);
bool ok = convertToProjectSuccess(rawResult);
```

代码引用使用文件名、类名、函数名、宏或协议命令等稳定符号，不依赖容易随修改失效的行号。

## 6. 预测—实测回填

只要排查过程中提出过预测，就必须在实验后回填。推荐使用表格：

| 预测来源 | 预测内容 | 实测结果 | 判定 | 证据 |
| --- | --- | --- | --- | --- |
| 某次代码审查/讨论 | 【填写】 | 【填写】 | 符合/不符合/未验证 | 【文件或日志】 |

以下内容都必须保留：

- 命中的预测；
- 被证伪的预测；
- 没有预测到但影响结论的新现象；
- 因证据不足而不能判定的项目。

预测错误不是文档缺陷，而是经验价值的一部分。删除错误预测会让后来的人失去判断边界，也会造成重复踩坑。

## 7. 假设坟场

被否决、撤回或降级的假设统一记录为：

```text
当时的说法 → 否决证据 → 当前表述
```

每条至少说明：

1. 假设当时为什么看起来合理；
2. 哪个实验、日志或源码事实与它冲突；
3. 它是被排除、降级为候选，还是换成了更准确的表述。

假设坟场不是为了追责，而是为了阻止已知错误方案重新进入设计和调试路径。

## 8. 原始材料与追溯

经验帖中的原始数据必须可检索、可回链：

- 串口原文、波形和 CSV 放在 `../波形与数据/`；
- 单次上电环境、激励和判据放在上级实验记录；
- 经验帖只摘录关键段，并注明完整文件名；
- 代码结论关联代码提交或稳定函数名；
- 文档新增后同步更新本目录 `_说明.md` 的索引和 `docs/00_文档总览.md` 的变更记录。

禁止把聊天转述、记忆中的数值或未保存的现场描述写成“原始日志”。确实只能转引时，必须标为相应证据等级并说明原始记录是否存在。

## 9. 经验帖完成定义

一篇经验帖只有满足以下条件，才能从草稿或挂账状态进入已验证状态：

- [ ] 文头状态、版本和证据声明完整；
- [ ] 病情、触发条件和分层边界清楚；
- [ ] 关键数值和结论能够回到原始材料；
- [ ] 初始假设、错误预测和转折点没有被删掉；
- [ ] 根因、修复和验证结果分别书写；
- [ ] `[A]`、`[B]`、`[C]`、`[D]` 没有越级使用；
- [ ] 预测—实测表已经回填，未验证项已挂账；
- [ ] 假设坟场已记录被否决的解释；
- [ ] 经验已提炼为可迁移的检查步骤；
- [ ] 调试日志索引和文档总览已同步；
- [ ] 关联代码、实验记录和提交能够互相追溯。
