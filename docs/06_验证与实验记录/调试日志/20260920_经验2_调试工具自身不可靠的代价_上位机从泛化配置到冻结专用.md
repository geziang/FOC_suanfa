## 0. 本篇只讲四条

1. **调试工具自身不可靠时，调试成本按故障数×工具故障数相乘**。本战役四起故障全部长在"工具链"上（串口解析、命令前缀、绘图管线、ADC 驱动），没有一起是电机算法问题——每一起都在消耗本应花在上层算法上的注意力。[转引实测 + B-代码事实]
2. **泛化上位机的每一个"可配置自由度"都是潜在的调试对象**。命令前缀一个界面输入框，两天内制造了参数全零、`unknown cmd err` 洪流、断连无法恢复三种现场。专用化路径 = 识别稳定不变量然后写死（前缀 `M`、115200-8N1、拉取模式、唯一启动器、启动自动开页），把操作面冻结到"选端口 + 点连接"。[B-代码事实，提交 `6a7cd3b`]
3. **跨层故障必须分层证伪，每层配一个"换个参数就能否决"的判据**：GUI 层看负载特征、链路层换降采样 1000、固件层勾掉 Cq/Cd。三层判据各否决/锁定一层，根因（ADC 双驱动冲突死循环）才能被唯一钉死。[转引实测 + B-代码事实]
4. **一行残缺数据是最贵的证据**：曲线行断在第 3 列（Vd 之后），与库 `FOCMotor::monitor()` 的打印顺序对齐，直接把断点映射到 `getFOCCurrents()` 调用处——"行内断点"比"整段日志"定位价值高一个量级。[转引实测 + B-代码事实]

## 1. 病情陈述

同一块板卡、同一份固件，2026-09-20 一天内先后出现四类异常，全部由"接上位机"触发：

- **不接上位机时一切正常**（shell 交互、1 行/秒心跳、电机控制）；
- ① 上位机连接初期：每条协议命令换回多行回执、串口刷屏（已在战役前段修复，作背景章）；
- ② 会话中途：`unknown cmd err` 以每秒 2~8 行刷屏，界面参数全零，断开重连**不能恢复**；
- ③ 绘图页勾 7 变量（含 Cq/Cd）点「开始」：固件瞬间全哑——无心跳、无应答、无曲线，**复位后 100% 复现，降采样 100 与 1000 无差别**；勾掉 Cq/Cd 即恢复正常；
- ④ 上位机日志每收一行协议文本抛一次 `TypeError`（`deviceTreeview.setModCenter`）。

## 2. 事实链

### 2.1 链路结构（协议两端源码实证，[B-代码事实]）

- 固件侧：`SerialShell` 与 SimpleFOC `Commander`（注册 ID `'M'`）共享同一串口；`StudioBridge::update()` 会话期独占执行 `cmd_.run()` + `motor.monitor()`；`PowerMonitor` 每秒经 `dengfoc_v4::readVin()`（arduino-esp32 官方 `analogReadMilliVolts`）读母线电压。[B]
- 上位机侧：`simpleFOCConnector.py` 所有下行命令统一走 `sendCommand(devCommandID + 命令体 + '\n')`；连接后 `StateUpdateRunner` 线程每周期发 `MG0~MG6` 七条状态查询；绘图开启时发 `MMD<降采样>` + `MMS<位图>`。[B]
- 库侧（SimpleFOC 2.2.1）：`FOCMotor::monitor()` 按位图打印 target → Vq → Vd → **（若含 Cq/Cd 位）调 `current_sense->getFOCCurrents()` 读 ADC** → Cq/Cd → vel → angle；ESP32 电流采样 `_readADCVoltageInline` 走库自带裸寄存器驱动 `adcRead()`（`esp32_adc_driver.cpp`，直接改写 SENS 寄存器、把 ADC1 强占为软件控制模式）。[B]

### 2.2 故障②的现场与判决材料（转引实测）

- 刷屏时段：`unknown cmd err` 每秒 2~8 行，成组 `Monitor |` 应答消失；
- 重连后：**无任何 pull config 应答**（参数全零），仅剩 `unknown cmd err`；
- `.SimpleFOCConfigTool.log` 的 `[SERIAL TX]` 记录：故障段 `command='MG0'`（缺 `M`），正常段 `command='MMG0'`——**线缆判据**；
- 错位解析痕迹：`MMD`→`MD` 落入库 D 轴电流 PID 分支 → `PID curr d| err`；`MMS`→`MS` 落入传感器分支 → `Sensor | err`。全文只有 MG/MD/MS 三类报错，其余命令被静默丢弃——与"首字母非 `M` 即无声"的 Commander 分发语义完全吻合。[转引 + B]

### 2.3 故障③的现场与判决材料（转引实测）

- 勾 7 变量（位图 `0x7F`）点「开始」后：固件零输出（连 1 行/秒心跳都停）；`.SimpleFOCConfigTool.log` 里由心跳触发的 `TypeError` 痕迹同步消失约 7 秒——**上位机一根线都没收到**（TX 线程正常，`MMG0~6` 持续在发）；
- 最早一次故障留下一行残缺曲线数据 `1.0000	1.0000	0.0000`——**断在第 3 列（Vd 之后）**，下一列正是需要读 ADC 的 Cq；
- **判决实验**（用户执行）：勾掉 Cq/Cd、保留 target/Vq/Vd/vel/angle → 曲线正常流动、心跳不断；降采样 1000 与 100 同样卡死（Cq/Cd 在场时）。[转引实测]

### 2.4 修复后状态（转引实测）

三组修复（§5）落地并重新烧录后，用户确认"串口已经正常"；Cq/Cd 勾回的完整复测记录尚未落盘（挂账 §9）。

## 4. 排查过程与转折点

1. **转折一（故障②）**：从"看固件打印"转向"看上位机 TX 日志"。`.SimpleFOCConfigTool.log` 的 `[SERIAL TX] command=...` 是触发型打印，一条即判前缀生死——比固件侧现象早一个因果层级。
2. **转折二（故障③第一层）**：读 `graphicWidget.py` 源码发现 `monitoringDataReceived` 逐行直连 `upDateGraphic`，每行做 7 曲线 `setData + updateItems + 手动 sigPlotChanged` 全量重绘且 `antialias=True`——GUI 瓶颈成立，动手解耦（提交 `4bfa29f`）。离屏功能冒烟全绿。
3. **转折三（否决 H2）**：用户回报"更新完成但还是卡"。新架构下 GUI 每秒工作量只剩几十分之一，仍卡 → 问题不在接收端 → 排查焦点移交数据源头。
4. **转折四（否决 H4）**：降采样 1000 仍死。0.8 KB/s 对 115200 是 7% 占用——带宽假说出局，同时"任何传输侧优化"都失去靶子。
5. **转折五（行内断点）**：回看最早残行 `1.0000	1.0000	0.0000`，列数断点与 `FOCMotor::monitor()` 源码打印顺序逐一对照——断点落在 `getFOCCurrents()` 调用前一行打印之后。结合"勾掉 Cq/Cd 即正常"的判决实验，唯一被钉住的路径是电流采样。
6. **转折六（驱动对质）**：读 `_readADCVoltageInline` 发现走库自带 `adcRead()`（裸寄存器），而 `dengfoc_v4::readVin()` 走官方 `analogReadMilliVolts()`——两套驱动同一块 ADC1。`__adcEnd()` 内 `while (DONE 位未置位);` 是无超时 busy-wait。触发面闭合验证：电压力矩模式下 loop() 内**唯一**调 `adcRead()` 的路径就是 monitor() 的电流列（setup 阶段采样对齐时库驱动刚独占初始化，故初始化不触发）。

## 5. 根因、修复与验证

### 5.1 根因陈述（[C-推断]，由判决实验与补丁生效支撑）

SimpleFOC 2.2.1 的 ESP32 电流采样自带裸寄存器 ADC 驱动（把 ADC1 强占为软件控制模式），与 arduino-esp32 2.0.4 官方 ADC 驱动（本项目 `readVin` 每秒使用一次）在同一块 ADC1 上交替接管；SAR 转换完成标志不再置位后，`__adcEnd()` 的无超时 busy-wait 死循环卡死 loopTask——串口、心跳、FOC 全停。上游 SimpleFOC 2.3.x 重写 ESP32 电流采样驱动即为此类冲突。触发条件精确闭合："绘曲线且勾选电流列"。

### 5.2 修复动作（分层各上一道闸，提交 `67329ea`）

**根因层（库本地补丁，已安装库文件、不在 git 内）**——`esp32_mcu.cpp` 的 `_readADCVoltageInline`：

```cpp
// [FocKit 本地补丁 2026-09-20] 原实现走本库自带的裸寄存器驱动 adcRead()，与
// arduino-esp32 2.x 官方 ADC 驱动（本工程 readVin 用 analogReadMilliVolts）在
// 同一块 ADC1 上冲突……改走官方 analogRead（同为 12bit 0..4095，尺度不变）。
uint32_t raw_adc = analogRead(pinA);
return raw_adc * _ADC_CONV;
```

## 7. 假设坟场

1. **GUI 逐行重绘是唯一瓶颈** → 解耦改造后仍卡死 → 降级为"真实存在但非致命的次要问题"，修复保留（架构正确性独立成立）。
2. **串口带宽饱和** → 降采样 1000 无差别 → 排除。但降采样 100 的 ~150 行/s 需求确实贴近 115200 天花板，TX 环形缓冲与限速闸保留为**防御层**，不因假说被否决而撤除。
3. **旧进程/跑错启动器导致新代码未生效** → 双启动器均走同一 `.venv` 源码 vbs → 排除；派生收益：目录清理防误触（挂账）与"断连≠重启、一次只开一个实例"的操作纪律。
4. **串口 TX 阻塞是独立根因** → ADC 补丁单独生效（转引）→ 降级为并发风险项；传输层硬化保留。

## 8. 方法论与迁移用法

1. **分层证伪，每层配"换个参数就能否决"的判据**：GUI 层（看每秒工作量）、链路层（降采样 1000 一票否决带宽说）、固件外设层（勾掉 Cq/Cd 一票锁定 ADC 路径）。没有判据的分层只是重新表述现象。
2. **双端日志互证**：固件探针（心跳、`[Studio]` 回执、残行）↔ 上位机 `.SimpleFOCConfigTool.log`（`[SERIAL TX]` 逐条、RX 侧痕迹如 TypeError 频率）。单边日志都会骗人：TX 正常 + RX 全无 = 数据没发出来；本例中 TypeError 的**消失**反而成了"零输入"的影子指标。
3. **行内断点定位法**：半行数据 + 库源码打印顺序 = 源码级断点。遇到"输出停在半句话"，先对照打印语句序列再想别的。
4. **可观测性裁剪**：常态静默（1 行/秒心跳）、按需 `dbg on`、回执节流——信号密度比信号总量重要；刷屏不是信息，是把判决证据淹死的噪声。
5. **调试工具专用化冻结原则**（本篇立意）：泛化工具每个可配置自由度都是调试对象 ×N。产品化路径 = 识别稳定不变量并写死（前缀 `M`、115200-8N1、拉取模式、唯一启动入口、启动自动开页），把人的注意力预算全部还给被调对象。判定一个自由度该不该冻：**"它有没有正确配置之外的第二种取值？"**——没有，就写死。
