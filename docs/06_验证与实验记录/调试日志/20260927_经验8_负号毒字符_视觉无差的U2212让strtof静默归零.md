# 经验8 · 负号毒字符：视觉无差的 U+2212 让 strtof 静默归零

> 专题：力控台参数写入静默失败（负档 tq 写不进）——Unicode 毒字符 × C 解析器零转换
> 状态：已对齐（机制层证据链闭合；"输入框中字符即 U+2212"为 C 级推断；判决实验已于 2026-09-28 上机回填 PASS，见 §6）
> 硬件 / 固件 / 依赖版本：DengFOC V4 + 2208；02 号 `FocKit_force_ctrl.ino` 第二轮（HEAD 8f1f71d）；上位机 SimpleFOCStudio-zh 力控台（`forceBench.py` + `simpleFOCConnector.sendCommand`）
> 一手数据：`../波形与数据/力控_raw负档写入失败_串口节选.txt`（本篇同批落盘）；正档对照 CSV：上位机 `exports/第一幕.csv`（tc 列 0.002/0.005/0.010 阶梯已生效）
> 证据可用性声明：串口节选源自 2026-09-27 用户会话粘贴当日落盘；TX 侧字节未抓取（`sendCommand` 无 hexdump 日志），毒字符身份为推断级；REF-15 字节检查为 xxd 直接输出（A 级）
> 姊妹篇 / 关联规范：EXP-04（写入必读回——本次立功的纪律源头）；REF-15 §5/§6（操作单曾是毒源，本批已勘正并新增教学项）

## 0. 本篇只讲几条

1. **strtof 对无法转换的字符串静默返回 0**，而 0 恰是合法力矩值——"回显齐全但存了 0"，在数据上无法区分"用户要写 0"与"解析失败" `[A+B]`
2. 中文环境下负号有（至少）三种字节：ASCII `-`（0x2D）、全角 `－`（U+FF0D）、数学负号 `−`（U+2212，UTF-8 为 `e2 88 92`），**肉眼几乎不可分**；本库文档 REF-15 中操作单用的正是 U+2212 `[A]`
3. 写入必读回（EXP-04 纪律）是这类坑的最后一张网：绿线 `tq=0.0000e+00` 不是"写成功"，是在报"没写进去"——本次就是靠它抓到的 `[A]`
4. 防再犯口诀：**数值手敲不粘贴、负号切英文输入法敲、回显必须看到负号** `[A，判决实验 2026-09-28 回填 PASS]`

## 1. 病情陈述

力控台 tq 输入框写入负值（-0.002 / -0.005 / -0.010）后，`[FC CFG]` 回显恒为 `tq=0.0000e+00`，探针 `tc` 恒 0.0000，电机无输出。**只在负值发生**；同一 UI、同一条命令路径写正值（+0.002 / +0.005 / +0.010）当场上屏生效；固件 reset 重连后复现依旧。

## 2. 事实链

时间线（全部见一手数据节选）：

1. 会话一（采幕1 堵转阶梯）：正档 +2/+5/+10 mN·m 逐档写入成功——回显 `tq=2.0000e-03 / 5.0000e-03 / 1.0000e-02` 依次跟随，CSV `tc` 列同步阶梯 `[A]`；
2. 会话二（补负档）：reset 重连后单独写 -0.002 / -0.005 / -0.010，含连点多批重试——**每批"写入"产生恰好 12 条 `[FC CFG]` 回显**（力控台 `write()` 是 12 参数逐条下发，每条触发一行全参数回显），`tq` 列全部为 `0.0000e+00`，探针 `tc` 恒 0 `[A]`；
3. 字节检查：REF-15 操作单中"−2/−5/−10"取 xxd 输出为 `e2 88 92 32 0d 0a`——负号字节是 `e2 88 92`（U+2212 数学负号），**不是**键盘减号 0x2D `[A]`；
4. 发送链：`simpleFOCConnector.sendCommand` 实现为 `(str(command) + '\n').encode('utf-8')` 原样直发，**零字符变换**——框里是什么字节，固件就收到什么字节 `[B]`；
5. 固件解析：`fcCommands` 中 `float v = strtof(argv[1], nullptr)`，**无 endptr 校验**、无失败分支 `[B]`；C99 §7.22.1.3 规定 strtof"若无可执行转换则返回零" `[B]`；
6. UI 控件：力控台 12 个参数框均为裸 `QLineEdit`，无验证器——任意 Unicode 均可进入 `[B]`。

毒字符样本（仅用于 §5 判决实验复制，**勿用于参数输入**）：

```text
−        ← U+2212 MINUS SIGN（e2 88 92）
```

## 3. 初始假设与误判

**假设一："固件无法接收负数。"** 看似合理的来源：现象字面就是"负数写不进"，且当时已另有一个"正档阶梯 iq 列死零"的未决疑点，容易归并成"力矩通道整体有问题"。隐含前提是"固件对负值有符号限制或限幅拦截"。**推翻证据**：`fcCommands` 的 tq 分支只是 `tqRaw = v`，无任何符号判断；且正数走完全相同的解析路径成功——若路径拒绝负数，正数也应异常 `[B+A]`。

**假设二："串口干扰截断了命令。"** 隐含前提是"写入时 12 条命令有丢失/截断"。**推翻证据**：每批恰好出现 12 条回显——命令全部到达且被 `fcCommands` 执行；若 tq 行被截断，该行要么无回显、要么解析出残缺值（如 `-0.0`），而实测是"回显出现 + 存储值恰为 0" `[A]`。

**假设三："固件状态异常，reset 能解决。"** 这是用户的第一次自救，方向来自"重启大法"。**推翻证据**：reset 重连后失败依旧——问题在输入的字节，不在固件状态 `[A]`。

## 4. 排查过程与转折点

**转折点一：数回显条数。** 复盘日志时发现"每批写入恰好 12 条 `[FC CFG]`"这个签名。它一步把问题从"命令没到/固件没收到"（传输层）推移到"命令到了、执行了、但 `v` 解析成了 0"（解析层）。数行数而不是看内容，是本次最快的定位动作。

**转折点二：xxd 看文档字节。** 对 REF-15"−2"取字节得 `e2 88 92`。这一步把怀疑对象从"固件行为"彻底转向"输入字符"，同时锁定了毒源——操作单本身。此前所有排查都默认"输入框里的是一个负号"，这个默认在中文环境下不成立。

**转折点三：代码链闭合。** 依次核查 `sendCommand`（原样 UTF-8 直发，零变换）→ `strtof` 语义（无转换返回 0）→ 回显行为（存 0 显示 0），三环扣上后，现象与机制严丝合缝：**回显齐全 = 命令执行了；回显为 0 = 解析结果为 0；正数成功 = 路径本身没病**。

## 5. 根因、修复与验证

**根因（机制层，已证）**：tq 输入框中的值字符串以 U+2212（或同类非 ASCII 负号）开头 → 上位机原样 UTF-8 直发 → 固件 `strtof("\xe2\x88\x920.002")` 零转换、静默返回 0.0 → `tqRaw=0` → 回显 `tq=0.0000e+00` `[A+B]`。

**根因（触发层，C 级推断）**：输入框中的负号确为 U+2212——最可能来源是从文档/聊天记录复制数值，或输入法符号页。无 TX hexdump 直接证据，按证据纪律标 C。**判决实验（2026-09-28 回填：PASS）**：英文输入法手敲 ASCII 负档写入，-0.002/-0.005/-0.010 三档全部生效（iq=−0.0625/−0.1562/−0.3125，电机 −53 rad/s 实转），见 §6 与 TST-04。桌面复跑命令（供读者）：

```text
看字符码点：python -c "print(hex(ord(input())))"   然后粘贴待查字符
strtof 判决：编译运行 strtof("\xe2\x88\x92" "0.002", &end)，观察返回 0 与 endptr 停在串首
```

（本机当日无可用编译器/Python 运行时，两条均未本地复跑，按 B 级标准条款支撑结论，上机判决实验回填后升级。）

**修复：代码不修（决策存档）。** 理由：①实验台性质，手敲 ASCII 负号绕过成本趋近零；②该失败模式已被"写入必读回"纪律网住（本次即例证）；③成熟产品的分层防御方案浓缩入 §8 供产品化时取用。若将来立项，首选固件端 `strtof` 加 endptr 校验（解析零长度即拒绝并回显错误行，约 5 行），一处保护所有串口入口。

**同批完成的防再犯（文档侧）**：REF-15 全文 17 处 U+2212 替换为 ASCII `-`（操作单去毒）；REF-15 §6"故意弄坏"清单新增第 6 条（粘毒字符看静默失败），把本坑变成教学素材。

## 8. 方法论与迁移用法

**为什么"这个上位机"会有输入法问题**：不是输入法的 bug——IME 忠实产出了它被要求产出的字符；是**整条链路上没有任何一层验证"这是个数"**：QLineEdit 是自由文本（无验证器）→ Python str 对 Unicode 透明 → 串口只管字节 → strtof 只认 ASCII 且静默返 0。中文环境只是让错误字节的出现概率从"可能"变成"几乎必然"。

**成熟产品的六层防御**（产品化时按序取用）：

| 层 | 做法 | 一句话 |
| --- | --- | --- |
| ① 控件即验证器 | 数值框用 QDoubleSpinBox（配 `QLocale.c()` 防欧语区小数点陷阱） | 非数字物理上敲不进 |
| ② 输入域感知 | Windows IMM32/TSF InputScope：控件声明"数字域"，IME 自动切半角；或焦点进入数字框强制切英文输入法 | 输入法替你把关 |
| ③ 边界正规化 | 入口一行 `unicodedata.normalize('NFKC', s)`——Unicode 标准兼容分解把 U+2212/U+FF0D/全角数字全部映射为 ASCII `[B]` | 一行代码消灭整类问题 |
| ④ 类型化协议+拒绝语义 | Modbus 异常码 0x03 / CANopen SDO abort / SCPI 错误队列——设备**永不静默默认** | "解析失败=拒绝+带原因报错" |
| ⑤ 写-读-比-告警闭环 | 工控 force 写入标配：写→回读→**程序比对**→不一致标红 | 程序当裁判，不靠人眼 |
| ⑥ i18n/IME 测试矩阵 | 全角、CJK 输入法、阿拉伯小数点进 QA 用例 | 把"操作问题"上保险 |

**C 解析惯例**：strtof/strtol 必带 endptr 并校验消费长度；**静默默认值是嵌入式 CLI 的经典坑**——尤其当默认值（0）恰好是合法业务值时，失败在数据上不可见。

**防呆（poka-yoke）视角**：凡是"靠操作员不踩坑才能跑通"的路径，都算设计留了坑。本项目的权衡是实验台阶段以纪律（写入必读回）代替防呆，此决策及其边界记录于 §5。

**迁移检查步骤**（遇到"参数写不进/写了没反应"）：
1. 数回显条数——判断命令是否到达（无回显=传输/路由问题；有回显=解析或存储问题）；
2. 看回显值与输入值是否一致——不一致即失败，别相信"有回显=写成功"；
3. 值含负号/小数点时，查字符字节（`hex(ord(c))`）而不是查意图；
4. 对照实验：同路径写一个无符号的简单正值，分离"路径病"与"字符病"。
